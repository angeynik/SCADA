# Пользователи, команды и журнал

Пользователи сервера, вход по паролю, единый путь записи в контроллеры (`commandGateway`) и журнал действий. Всё хранится в PostgreSQL. Вход по паролю нужен OPC UA уже сейчас, а с этапа 8 — и интерфейсу.

## Роли

| Уровень | Роль | Что разрешено |
|---|---|---|
| 1 | `viewer` | Просмотр значений, тревог, архива |
| 2 | `operator` | + команды (пуск/стоп, режим), квитирование тревог |
| 3 | `engineer` | + уставки, расписания, настройка тревог, журнал |
| 4 | `admin` | + пользователи, доверие сертификатам OPC UA, конфигурация объекта |

Какой уровень нужен для записи параметра, задаёт шаблон (`writeLevel`, по умолчанию 3 — инженер). Например, в `AhuType` команда пуск/стоп и методы `Start`/`Stop` доступны с уровня 2, уставка температуры — с уровня 3.

## База данных

| Параметр | По умолчанию | Описание |
|---|---|---|
| `PG_URL` | пусто | Адрес PostgreSQL **без пароля**: `postgresql://scada@127.0.0.1:5432/scada` или через сокет `postgresql:///scada?host=/var/run/postgresql`. Пусто — сервер без БД: пользователей нет, журнал только в логе |
| `PG_POOL_MAX` | `10` | Наибольшее число соединений (2–100) |
| `BCRYPT_ROUNDS` | `12` | Трудоёмкость bcrypt (10–15). 12 — около 0,7 с на проверку пароля; проверка не блокирует сервер |
| `AUTH_MAX_FAILURES` | `5` | Неудачных попыток подряд до временной блокировки имени |
| `AUTH_LOCK_MS` | `60000` | Время блокировки, мс |

**Пароль БД** в `PG_URL` и `conf.env` не пишется: сервер откажется запускаться. Варианты:
- `~/.pgpass` пользователя, от которого работает служба (права `600`): `127.0.0.1:5432:scada:scada:<пароль>`;
- переменная `PGPASSWORD` в окружении службы (`systemctl edit` → `Environment=` или `EnvironmentFile=` с правами `600`);
- вход по сокету с `peer`-аутентификацией, если имя пользователя ОС совпадает с ролью БД, — тогда пароль не нужен вообще.

**Подготовка БД** (один раз, администратор PostgreSQL):

```sql
CREATE ROLE scada LOGIN PASSWORD '…';
CREATE DATABASE scada OWNER scada;
```

Таблицы создаёт сервер: при запуске (и при запуске `tools/userAdmin`) он применяет миграции из `storage/migrations/` по номеру. Применённые записываются в `schema_migrations`. Если два узла стартуют одновременно, второй ждёт первого: миграции разводит рекомендательная блокировка PostgreSQL.

Миграцию нельзя изменить после применения — сервер не запустится. Изменения схемы вносятся только новой миграцией. Если в базе есть миграции, которых не знает сервер (например, после отката версии), сервер тоже не запустится.

Без БД при запуске сервер не стартует (код выхода 1, «нет подключения к PostgreSQL …»). Если БД пропала во время работы, процесс не падает:
- вход отвечает «база пользователей недоступна»;
- уже открытые сессии продолжают работать;
- запись журнала уходит только в лог с ошибкой «журнал не записан в БД».

## Эмулятор PostgreSQL для разработки

На машине разработчика рабочая БД не нужна. `tools/pgEmulator.js` поднимает отдельный экземпляр PostgreSQL из программ, установленных на машине. Как Modbus- и BACnet-эмуляторы, он изображает рабочий сервер:

- роль `scada` без прав суперпользователя, базы `scada` (работа) и `scada_test` (тесты);
- слушает только Unix-сокет в своём каталоге: TCP не открывается, общий PostgreSQL машины не затрагивается;
- данные (пользователи, журнал) сохраняются между запусками;
- под root программы работают от пользователя ОС `postgres`, каталог — `/var/tmp/scada-pg-emu`, у обычного пользователя — `DATA_DIR/pg-emu`.

```bash
npm run pg:start          # создать при первом запуске и запустить; печатает PG_URL для conf.env
npm run pg:status
npm run test:pg           # весь набор тестов вместе с тестами PostgreSQL
node tools/pgEmulator.js exec -- npm start                          # сервер с БД эмулятора
node tools/pgEmulator.js exec -- node tools/userAdmin.js add admin --role admin
npm run pg:stop
node tools/pgEmulator.js reset --yes   # удалить все данные эмулятора
```

`exec -- <команда>` при необходимости запускает эмулятор и выполняет команду с `PG_URL` и `TEST_PG_URL` эмулятора в окружении. Сигнал остановки (Ctrl+C, SIGTERM) передаётся команде, и сервер останавливается корректно. Вместо `exec` можно один раз записать `PG_URL` из `pg:start` в `conf.env`.

Чем эмулятор отличается от объекта:

| | Эмулятор | Объект |
|---|---|---|
| Вход в БД | по сокету без пароля (`trust`) | пароль через `PGPASSWORD` или `~/.pgpass`, либо `peer` |
| Сеть | только сокет | TCP или сокет, по решению администратора |
| TimescaleDB | только если расширение установлено на машине (`pg:status` показывает) | ставится вместе с PostgreSQL (нужно для архива, этап 6) |
| Резервные копии | нет | `docs/deploy.md` (этап 10) |

Сервер и миграции работают одинаково: перенос на рабочий PostgreSQL — это только другой `PG_URL` и пароль в окружении службы.

## Первый администратор и управление пользователями

```bash
node tools/userAdmin.js add admin --role admin --name "Администратор"   # пароль вводится дважды, без эха
node tools/userAdmin.js add ivanov --role engineer --name "Иванов И. И."
node tools/userAdmin.js list
node tools/userAdmin.js role ivanov operator
node tools/userAdmin.js passwd ivanov
node tools/userAdmin.js rename ivanov "Иванов Иван"
node tools/userAdmin.js disable ivanov        # enable — разблокировать
node tools/userAdmin.js remove ivanov
echo "$PASS" | node tools/userAdmin.js passwd ivanov --password-stdin   # из скрипта
```

- **Имя пользователя:** 2–64 знака — латинские буквы, цифры, `.`, `_`, `-`.
- **Пароль:** не короче 8 знаков и не длиннее 72 байт (это предел bcrypt). В аргументах командной строки пароль не принимается: его видно в списке процессов.
- **Последний действующий администратор.** Его нельзя понизить, заблокировать или удалить. Проверка идёт в транзакции, поэтому два одновременных изменения её не обойдут.
- **Изменения из инструмента действуют без перезапуска.** Инструмент работает напрямую с БД. Запущенный сервер получает уведомление (`NOTIFY scada_users`) и закрывает все сессии изменённого пользователя.
- **Журнал.** Каждое изменение попадает в журнал с источником `userAdmin (ОС: <пользователь>)`.

## Вход

`services/auth` — один для OPC UA и будущего WebSocket.

- **Ответ клиенту и запись в лог.** Неверное имя, неверный пароль и заблокированная учётная запись дают клиенту один и тот же ответ: так нельзя подобрать существующие имена. В лог записывается настоящая причина. Если пользователя с таким именем нет, пароль всё равно сравнивается с хешем-заглушкой: по времени ответа тоже нельзя понять, есть ли такое имя.
- **Блокировка.** После `AUTH_MAX_FAILURES` неудач подряд имя блокируется на `AUTH_LOCK_MS`. В это время не принимается даже верный пароль. Ошибка БД неудачей не считается.
- **Пароли в лог не попадают никогда.**

## Единый путь записи (commandGateway)

Любая запись — из OPC UA, а позже из интерфейса, расписаний и сценариев — проходит одни и те же проверки по порядку:

| № | Проверка | Код отказа |
|---|---|---|
| 1 | Тег существует и `access: "rw"` | `NOT_FOUND`, `READ_ONLY` |
| 2 | Пользователь вошёл и его уровень не ниже `writeLevel` | `FORBIDDEN` |
| 3 | Тип значения (`Boolean`, целое в пределах типа, число) | `TYPE_MISMATCH` |
| 4 | `min`/`max`, номер состояния из `states` | `OUT_OF_RANGE` |
| 5 | Узел основной (резервирование, этап 9) | `NOT_PRIMARY` |
| 6 | Драйвер включён и пишет; контроллер подтверждает повторным чтением | `NOT_CONNECTED`, `OUT_OF_RANGE`, `WRITE_FAILED` |
| 7 | Запись в журнал | — |

- **Значение для клиентов** меняется только после подтверждения контроллером и равно тому, что прочитано из контроллера.
- **Снятие команды BACnet** (`release`, NULL в свой приоритет) проходит те же проверки, кроме 3–4. Для Modbus оно не поддерживается (`NOT_SUPPORTED`).
- **При остановке сервера** шлюз первым перестаёт принимать команды (`NOT_CONNECTED`, «сервер останавливается») и ждёт завершения уже начатых. Только потом останавливаются драйверы.

## Журнал

Таблица `journal`:

| Поле | Содержимое |
|---|---|
| `ts` | Время |
| `username` | Кто: имя пользователя, `null` — анонимно или инструмент |
| `source` | Откуда: `opcua/UaExpert`, `opcua/UaExpert:Start`, `userAdmin (ОС: root)` |
| `action` | `write`, `release`, `user.create`, `user.role`, `user.password`, `user.disable`, `user.enable`, `user.rename`, `user.remove` |
| `tag_id` | Тег (для команд) |
| `old_value`, `new_value` | Было → стало (jsonb): число, логическое, строка или объект для действий с пользователями |
| `ok`, `code`, `message` | Результат: успех или код отказа с пояснением; при успехе — «подтверждено X», если контроллер вернул не то, что записывали |

В журнал попадает каждая попытка, в том числе отклонённая (`FORBIDDEN`, `OUT_OF_RANGE`), и каждое действие с пользователями. Пароли и хеши не попадают. Каждая запись дублируется строкой в лог:

```
[Journal] - write - ivanov@opcua/UaExpert B1/AHU-17/SupplyTempSp: 21 → 22.5, выполнено
[Journal] - write - petrov@opcua/UaExpert B1/AHU-17/SupplyTempSp: 22.5 → 26, отказ FORBIDDEN (недостаточно прав: нужен уровень 3, у petrov — 2)
```

Выборка журнала для интерфейса (`get/journal`) — этап 8. До этого — SQL-запросом:

```sql
SELECT ts, username, source, tag_id, old_value, new_value, ok, code FROM journal ORDER BY id DESC LIMIT 50;
```

## Тесты с БД

Тесты PostgreSQL (`tests/integration/storage.integration.js` и сквозной тест в `server.integration.js`) запускаются, только если задан `TEST_PG_URL`; без него они пропускаются. Каждый запуск создаёт свою временную схему и удаляет её, поэтому подойдёт и общая тестовая база:

```bash
TEST_PG_URL=postgresql://scada@127.0.0.1/scada_test npm test
npm run test:pg     # то же с эмулятором PostgreSQL
```
