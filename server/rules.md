# Инструкции для сервера SCADA BMS

Сервер верхнего уровня BMS: опрашивает контроллеры вентустановок (ОВЕН — Modbus TCP, Metasys N30 — BACnet/IP), ведёт модель здания, тревоги и архив и отдаёт данные по OPC UA (внешние клиенты) и по WebSocket (свой интерфейс из `../client`). План работ — `PLAN.md`, обоснование выбора — `../2026-11-25-bms-own-opcua-server.md`.

## Границы ответственности
- Сервер — только диспетчерский уровень. Защита от замораживания, аварийные блокировки и расписание по умолчанию работают в контроллерах. Сервер не реализует защитные функции и не должен быть нужен для безопасной работы установки: его отказ или перезапуск не опасен для оборудования.
- Сервер не программирует контроллеры и не меняет их логику. Он только читает значения и пишет команды и уставки, разрешённые конфигурацией.

## Стек и окружение
- Node.js 24 LTS (`engines: >=24.9`), CommonJS: `require` / `module.exports`, в каждом модуле `'use strict'`. Версия 24.9+ нужна потому, что node-opcua — ESM-пакет: сервер загружает его обычным `require()`, а Jest умеет это только на Node 24.9+ с флагом `--experimental-vm-modules` (его ставит `npm test`).
- Основные библиотеки: `node-opcua` (OPC UA-сервер), `modbus-serial` (Modbus TCP), `@bacnet-js/client` (BACnet/IP), `pg` (PostgreSQL + TimescaleDB), `ws` (WebSocket для клиента), `joi` (схемы), `dotenv`, `bcryptjs`, `jsonwebtoken`; тесты — `jest`.
- Новая зависимость — только по согласованию с пользователем. Перед добавлением проверить лицензию и активность проекта. Разрешены MIT, ISC, BSD, Apache-2.0. LGPL — по согласованию. GPL и AGPL запрещены, потому что сервер может тиражироваться.
- Настройки — только из `conf.env` (dotenv), образец — `conf.env.example`. Файл ищется рядом с `server.js`, другой путь задаёт `CONF_ENV_FILE`. Переменная окружения терминала перекрывает `conf.env`, и при старте сервер пишет в лог имена перекрытых переменных. Недопустимое значение параметра — ошибка при старте, сервер не запускается. Новый параметр: описать в `SCHEMA` в `services/config.js` со значением по умолчанию и добавить в `conf.env.example`. Другие модули `process.env` не читают, а получают `config` от `server.js`.
- Секреты (`JWT_SECRET`, пароль БД, пароли пользователей OPC UA, закрытые ключи сертификатов) хранятся только в окружении и в каталоге PKI. В git, логи, ответы клиентам и сообщения об ошибках они не попадают. Пароль БД — только `PGPASSWORD` в окружении службы или `~/.pgpass`; `PG_URL` с паролем — ошибка настроек.
- Конфигурация объекта (шаблоны установок, экземпляры, привязки) — JSON-файлы в `CONFIG_DIR`. Пользователи, журналы, тревоги и архив — в PostgreSQL.

## Стиль кода
- ES6+, `async/await`, отступ 2 пробела, одинарные кавычки, точки с запятой.
- Только `let` и `const`, `var` не использовать.
- Комментарии на русском и по делу: шапка модуля (назначение, формат данных) и неочевидные решения. Закомментированный код не оставлять.
- DOM API и браузерные объекты не использовать.
- Сервис с зависимостями оформляется как фабрика `createXService(deps)`. Синглтон-обёртку собирает только `server.js`. Так любой модуль тестируется с фейками.
- Время внутри сервера — `Date` или миллисекунды UTC. В лог и клиентам — ISO 8601. Местное время нужно только для расписаний и отчётов, часовой пояс объекта — `timezone` в `site.json`.

## Логирование
- Логирование — через `services/logger.js`: `logInfoMessage`, `logDevMessage`, `logErrorMessage`. Формат: `[Модуль] - функция - сообщение`. Функции принимают несколько аргументов (объекты выводятся через `util.inspect`).
- Уровень `LOG_LEVEL`: `error` — только ошибки; `info` (по умолчанию) — ошибки и info; `dev` — всё; `none` — ничего (только для тестов).
- Вызовы `console.*` (отладочный вывод) добавляет и удаляет только пользователь. Claude их не добавляет, не удаляет и не переводит на `logger.js`; при ревью проверяет только корректность (не роняют процесс, не выводят секреты, не мешают тестам). Собственные сообщения Claude пишет через `logger.js`.
- Обрыв связи с контроллером логируется один раз при переходе в `bad` и один раз при восстановлении, а не на каждый неудачный опрос. Первое подключение после запуска — на уровне `dev`.
- Логгер не бросает исключений: ошибка канала вывода (EPIPE) отключает запись в этот канал. Иначе ошибка записи стала бы `uncaughtException`, а его запись в тот же канал — новой ошибкой.
- Входящие сообщения клиентов логировать только через `logger.redactSecrets()`.

## Структура проекта
- `server.js` — точка входа: читает конфигурацию, собирает сервисы, запускает и останавливает их. Бизнес-логики не содержит.
- `services/` — общие сервисы: `config` (conf.env), `logger`, `version` (номер выпуска и коммит), `lifecycle` (запуск по порядку, остановка в обратном порядке с таймаутом), `processHandlers` (сигналы, необработанные ошибки), `validate` (схемы Joi), `auth` и `userStore` (пользователи и роли), `commandGateway` (единый путь записи), `journal` (журнал действий), `redundancy` (роль узла).
- `core/` — модель и данные: `modelSchema` (схемы Joi файлов конфигурации), `modelLoader` (шаблоны, карты и экземпляры → теги), `quality` (качество и коды, соответствие StatusCode OPC UA), `tagStore` (текущие значения, качество, подписки), `alarmEngine`, `scheduler`.
- `drivers/` — драйверы контроллеров: `modbusTcp/`, `bacnetIp/`. Каждый драйвер реализует контракт из раздела «Драйверы».
- `opcua/` — OPC UA-сервер: `addressSpace` (типы и экземпляры), `alarms` (Alarms & Conditions), `history` (Historical Access), `security` (PKI, пользователи).
- `ws/` — WebSocket-шлюз для клиента: соединения, маршрутизация, обработчики запросов.
- `storage/` — PostgreSQL: `db` (пул, транзакции, LISTEN/NOTIFY), `migrate` и `storage/migrations/NNN_имя.sql`; позже `historian` (запись архива пакетами) и тревоги. Пользователи — `services/userStore`, журнал — `services/journal`.
- `config/` — образцы конфигурации объекта (`*.example.json`). Рабочая конфигурация объекта — вне репозитория (`CONFIG_DIR`).
- `tools/` — инструменты, сервер их не загружает: `checkModel` (проверка конфигурации объекта), `importTags` (таблица CSV → instances/*.json), `modbusEmulator` (N контроллеров по карте), `modbusDiag` (чтение точек установки или сырых регистров), `bacnetEmulator` (N устройств BACnet по шаблону), `bacnetDiscover` (поиск устройств, список объектов → черновик CSV, проверка привязок установки), `opcuaPki` (сертификаты OPC UA: список, доверие, отзыв), `userAdmin` (пользователи: первый администратор, роли, пароли, блокировка), `pgEmulator` (отдельный экземпляр PostgreSQL для разработки и тестов: только сокет, роль `scada`, базы `scada` и `scada_test`), `lib/` (разбор CSV, короткая запись точек, эмуляторы `modbusSlave` и `bacnetDevice`); позже — нагрузочный тест. Инструменты пишут в stdout/stderr напрямую и возвращают код выхода.
- `docs/` — инструкции: `model.md` (модель и конфигурация), `modbus-tcp.md`, `bacnet.md`, `opcua.md`, `users.md` (пользователи, команды, журнал), `ws-protocol.md`, `alarms.md`, `archive.md`, `deploy.md`. Если меняется поведение или параметр, описанный в инструкции, инструкция обновляется в том же изменении.
- `tests/` — Jest: `unit/<модуль>.test.js`, `integration/*.integration.js`, общий `setup.js`, помощники — в `helpers/`.
- В git не попадают: `conf.env`, `pki/`, `data/`, `logs/`, рабочая конфигурация объекта.

## Модель данных
- Иерархия: объект (`site.json`) → тип установки (шаблон, например `AhuType`) → экземпляр установки → тег. Привязка к контроллеру — в карте (`maps/`, общая для контроллеров одной модели) и в экземпляре (свои точки). Формат файлов и все проверки — `docs/model.md`.
- **Идентификатор тега** — `<объект>/<установка>/<параметр>`, например `B1/AHU-17/SupplyTemp`. Каждая часть соответствует `^[A-Za-z0-9_-]{1,64}$`. Этот же идентификатор служит строковым NodeId в OPC UA (`ns=<ns>;s=B1/AHU-17/SupplyTemp`) и ключом в архиве.
- **Главный принцип миграции:** идентификатор тега не зависит от источника. При переводе установки с N30 (BACnet) на ОВЕН (Modbus) меняется только привязка `source`, а идентификатор, NodeId, архив, тревоги и экраны остаются прежними. Изменение, которое ломает этот принцип, не принимается.
- Тег: `id`, `dataType` (`Boolean`, `Int16`, `UInt16`, `Int32`, `UInt32`, `Float`, `Double`, `String`), `access` (`r` | `rw`), `unit`, `min` и `max` (для записи), `writeLevel`, `states`, `deadband`, `archive` (режим и мёртвая зона), `alarms` (условия), `source` (драйвер, параметры связи, точка). Масштаб (`scale`, `offset`) — свойство точки, а не параметра: у ОВЕН и N30 одно и то же значение может храниться по-разному.
- Значение тега: `{ value, quality, code, sourceTs, serverTs }`. Качество — `good` | `uncertain` | `bad`, код причины — из `core/quality.js` (`NOT_CONNECTED`, `COMM_ERROR`, `CONFIG_ERROR`, `BAD_VALUE`, `DEVICE_FAULT`, `STALE`, `OUT_OF_SERVICE`). Каждый код однозначно отображается в StatusCode OPC UA (`toOpcUaStatus`). Новый код добавляется только в `core/quality.js` вместе с StatusCode и строкой в `docs/model.md`. При потере связи значение не «замораживается» как хорошее: качество становится `bad`, последнее значение сохраняется с этим качеством.
- Конфигурация объекта проверяется схемой Joi при загрузке. Ошибка в одном экземпляре отключает только этот экземпляр (с ошибкой в логе), а не весь сервер; ошибка в шаблоне или карте отключает их установки. Повтор идентификатора установки отключает все её копии. Нет `site.json` — сервер не запускается. Сообщения об ошибках конфигурации — на русском (`MESSAGES` в `modelSchema.js`), их читает инженер.
- Пример `config/example` обязан загружаться без ошибок (это проверяет тест). Меняется формат — меняются пример, `docs/model.md` и тесты в том же изменении.

## Драйверы
- Контракт драйвера (фабрика `createXDriver(deps)`): `start()`, `stop()`, `write(tagId, value) → Promise<{ ok, code, message }>`, `status()`; у драйверов с приоритетами (BACnet) — ещё `release(tagId)`, снятие команды. Новые значения драйвер передаёт только в `tagStore.update(tagId, value, { quality, code, sourceTs })`, обрыв связи — `tagStore.setQuality(tagId, 'bad', 'COMM_ERROR')`. Масштаб точки (`scale`, `offset`) применяет драйвер: в `tagStore` попадает значение в единицах параметра.
- Драйвер не обращается к OPC UA, WebSocket, БД и другим драйверам. Связь — только через `tagStore` и `commandGateway`.
- Ошибка драйвера или одного контроллера не роняет процесс и не мешает остальным контроллерам. Переподключение — с нарастающей паузой (от 1 с до `RECONNECT_MAX_MS`). Связь считается восстановленной только после успешного чтения, а не после TCP-подключения.
- Ответ `write` — `{ ok: true, value }` (значение после подтверждения) или `{ ok: false, code, message }`; коды драйвера: `NOT_CONNECTED`, `OUT_OF_RANGE`, `WRITE_FAILED`, `NOT_FOUND`.
- Каждому драйверу — тесты с транспортом-подделкой (`tests/unit/`) и интеграционные с эмулятором из `tools/lib/`.
- **Modbus TCP (ОВЕН)** — `drivers/modbusTcp/`, подробно `docs/modbus-tcp.md`:
  - одно TCP-соединение и одна очередь запросов на контроллер (`host:port`); запросы к одному контроллеру не пересекаются, запись идёт раньше очередных чтений;
  - соседние точки объединяются в один запрос (разрыв до `MODBUS_MAX_GAP`, не больше 125 регистров или 2000 битов); если контроллер отвергает блок исключением, блок разбивается на запросы по одной точке, отвергнутая точка получает `bad/CONFIG_ERROR`;
  - порядок байт и слов задаётся в карте или экземпляре (`byteOrder`), а не в коде;
  - таймаут ответа `MODBUS_TIMEOUT_MS`; после `MODBUS_FAIL_LIMIT` неудач подряд теги контроллера получают `bad/COMM_ERROR`;
  - сокет создаёт драйвер (`transport.js`), чтобы подключение к недоступному адресу прерывалось через `MODBUS_CONNECT_TIMEOUT_MS`.
- **BACnet/IP (N30)** — `drivers/bacnetIp/`, подробно `docs/bacnet.md`:
  - один BACnet-клиент (UDP-сокет) на процесс: на порту 47808 может слушать только один процесс; очередь запросов — на устройство (номер `device`), запись раньше очередных чтений; одновременно не больше 64 запросов на сокет;
  - перед опросом устройство опознаётся чтением объекта `device` (номер и `maxApduLengthAccepted`); адрес без `address` — по Who-Is/I-Am;
  - основной способ — подписка `SubscribeCOV` с продлением на половине `BACNET_COV_LIFETIME_S`; если подписка не принята — опрос `ReadPropertyMultiple` (`presentValue` + `statusFlags`) с периодом `BACNET_POLL_MS`; при остановке свои подписки снимаются;
  - размер запроса `ReadPropertyMultiple` — по `maxApdu` устройства без сегментации и не больше `BACNET_MAX_OBJECTS`; отказ устройства — деление запроса пополам;
  - `statusFlags.fault` → `bad/DEVICE_FAULT`, `outOfService` → `uncertain/OUT_OF_SERVICE`;
  - состояния `multiState*` в BACnet — с 1; если в шаблоне с 0, у точки `offset: -1` (так тег не меняется при переводе на ОВЕН);
  - запись `presentValue` — только с приоритетом точки или `BACNET_WRITE_PRIORITY` (по умолчанию 8, «ручное управление оператора»); приоритеты 1–7 сервер не использует никогда (проверяют схема, настройки и драйвер); снятие команды — `release(tagId)`, запись `NULL` в свой приоритет.

## Команды и запись
- Любая запись в контроллер (OPC UA, WebSocket, расписание, сценарий) выполняется одним механизмом — `commandGateway.execute({ tagId, value, user, source })`. Новый источник команд подключать только через него, драйвер напрямую не вызывать.
- Порядок проверки: тег существует и `access: rw` → права пользователя → тип, диапазон `min`/`max` и `states` → узел основной (см. «Резервирование») → запись в драйвер → подтверждение повторным чтением → запись в журнал. `tagStore` обновляет драйвер значением из подтверждения.
- Методы установки (`methods` шаблона: пуск, стоп) — запись заданного значения в параметр `rw` через тот же `commandGateway`, права — `writeLevel` параметра.
- Значение для клиентов меняется только после подтверждения устройством. При отказе инициатор получает ошибку с кодом (`NOT_FOUND`, `READ_ONLY`, `FORBIDDEN`, `TYPE_MISMATCH`, `OUT_OF_RANGE`, `NOT_PRIMARY`, `NOT_CONNECTED`, `NOT_SUPPORTED`, `WRITE_FAILED`), значение не меняется.
- Каждая команда, в том числе отклонённая, попадает в журнал (`services/journal`): кто, откуда, тег, старое → новое значение, результат. Действия с пользователями — тоже. Если БД недоступна, запись остаётся в логе с ошибкой, команда не отменяется.
- При остановке шлюз первым перестаёт принимать команды и дожидается начатых, затем останавливаются драйверы.

## OPC UA
- URI пространства имён — `OPCUA_NAMESPACE_URI` (по умолчанию `urn:scada-bms:model`). Индекс пространства имён клиенты получают из таблицы `NamespaceArray`, в коде его не зашивать.
- Типы установок — ObjectType (`AhuType` и др.), экземпляры — Object в папке объекта. NodeId экземпляров и переменных строковый и равен идентификатору тега: при перезапуске и смене конфигурации NodeId не меняется.
- Тревоги — Alarms & Conditions (подтверждение квитированием `Acknowledge`), архив — Historical Access из `storage/historian`.
- Безопасность:
  - в рабочем режиме разрешены только `Sign` и `SignAndEncrypt` (`Basic256Sha256`, `Aes128_Sha256_RsaOaep`, `Aes256_Sha256_RsaPss`); режим `None` и анонимный вход — только при `OPCUA_ALLOW_INSECURE=true` для разработки, и сервер пишет об этом предупреждение при старте;
  - вход по имени и паролю из того же `userStore`, права — по ролям из раздела «Права доступа»;
  - сертификаты и доверенные клиенты — в `PKI_DIR`, новые клиенты по умолчанию попадают в `rejected` и доверяются вручную.
- Порт `OPCUA_PORT` (по умолчанию 4840), интерфейс `OPCUA_INTERFACE` — в сети клиентов.
- Реализация — `opcua/` (подробно `docs/opcua.md`): `nodes.js` — соответствие модели и узлов (чистые функции), `addressSpace.js` — узлы из модели, `values.js` — значения из `tagStore`, `index.js` — сервер, PKI, вход пользователей. Вид переменной: целочисленный параметр с `states` — `MultiStateValueDiscreteType`, числовой — `BaseAnalogType` (`EngineeringUnits` по коду UNECE, `EURange` из `min`/`max`), остальные — `BaseDataVariableType`.
- Значение и StatusCode переменной берутся только из `tagStore` (подписка на изменения), своих значений OPC UA не хранит. Запись из OPC UA — только через `commandGateway` (этап 5); до этого все переменные `CurrentRead`.
- node-opcua загружается около 1,5 с, поэтому `server.js` подключает `opcua/` только при `OPCUA_ENABLED=true`. Собственный вывод библиотеки перенаправлен в `logger.js` (предупреждения — `dev`, ошибки — `error`).
- Доверие сертификату клиента — `tools/opcuaPki.js` (перенос из `rejected` в `trusted/certs`), автоматическое доверие (`automaticallyAcceptUnknownCertificate`) не включать.

## Обмен с клиентом по WebSocket
- Браузер не работает с OPC UA напрямую, поэтому клиент (`../client`) получает данные через WebSocket-шлюз сервера (`WS_PORT`). Шлюз использует те же `tagStore`, `commandGateway`, `alarmEngine` и `historian`, что и OPC UA. Своей логики данных у шлюза нет.
- Кадр — текстовый JSON (UTF-8): `{ "type": "...", "request": "...", "payload": { ... }, "time": "..." }`. `payload` — всегда объект, `time` добавляет сервер. Бинарные кадры не используются.
- `type`: от клиента — `auth`, `get`, `post`; от сервера — `response`, `error`, `info`, `push`.
- Первичный набор запросов: `auth/login`, `auth/resume`, `auth/logout`; `get/model`, `get/values`, `get/history`, `get/alarms`, `get/journal`; `post/subscribe` (список тегов или установок), `post/write`, `post/ackAlarm`. Push от сервера: `push/values` (пакет изменений не чаще `WS_PUSH_INTERVAL_MS`), `push/alarm`.
- Ответ — `response/<request>`, ошибка — `error/<request>` с `payload: { code, message }`. `code` — стабильный машинный код, `message` — текст для пользователя. Внутренние детали и стеки клиенту не отправлять.
- Протокол описывается в `docs/ws-protocol.md` — это договор с клиентом. Новый запрос добавляется сразу во все места: обработчик, уровень доступа, схема Joi, тесты, `docs/ws-protocol.md`. Изменения совместимые: поля и запросы добавляются, смысл существующих не меняется.
- Невалидные сообщения молча отбрасываются (с записью в лог). Клиенту с переполненным буфером (`bufferedAmount` больше `WS_MAX_BUFFER`) пакет значений пропускается, следующий пакет придёт полным.

## Права доступа
| Уровень | Роль | Что разрешено |
|---|---|---|
| 1 | `viewer` | Просмотр значений, тревог, архива |
| 2 | `operator` | + команды (пуск/стоп, режим), квитирование тревог |
| 3 | `engineer` | + уставки, расписания, настройка тревог, журнал |
| 4 | `admin` | + пользователи, доверие сертификатам OPC UA, конфигурация объекта |

- Уровень, нужный для записи, задаётся в шаблоне тега (`writeLevel`, по умолчанию 3). Для каждого нового запроса WebSocket и метода OPC UA уровень задаётся явно.
- Пароли — только bcrypt (`BCRYPT_ROUNDS`, асинхронно). При смене роли, пароля, блокировке или удалении все сессии пользователя отзываются: `userStore` рассылает `NOTIFY scada_users`, OPC UA и WebSocket закрывают сессии этого пользователя (изменение из `tools/userAdmin` в другом процессе тоже). Нельзя удалить, заблокировать или понизить последнего действующего администратора — проверка в одной транзакции с `SELECT … FOR UPDATE`.
- Вход — только через `services/auth`: клиенту причина отказа не раскрывается (`BAD_CREDENTIALS`), в лог — раскрывается; после `AUTH_MAX_FAILURES` неудач имя блокируется на `AUTH_LOCK_MS`. Анонимная сессия (только в режиме разработки OPC UA) писать не может.

## Тревоги
- Условие тревоги задаётся в шаблоне: предел (`hi`, `lo`, `hihi`, `lolo`), дискретное состояние или качество `bad`. Есть гистерезис и задержка срабатывания, чтобы тревога не «дребезжала».
- Состояния: активна/неактивна × квитирована/не квитирована. Приоритет 1–1000 (как Severity в OPC UA): 1–250 — информация, 251–500 — предупреждение, 501–800 — авария, 801–1000 — критическая.
- Каждое изменение состояния и квитирование — в журнал тревог (БД) с пользователем и временем. Активные тревоги восстанавливаются после перезапуска.

## Архив
- PostgreSQL + TimescaleDB. Схема меняется только миграциями в `storage/migrations/` (по номеру, вперёд). Ручные изменения схемы запрещены.
- Запись по изменению с мёртвой зоной (`archive.deadband`) или по периоду (`archive.periodMs`). Пишется пакетами (`ARCHIVE_FLUSH_MS`, `ARCHIVE_BATCH`), не по одному значению.
- Если БД недоступна, значения копятся в ограниченном буфере в памяти (`ARCHIVE_BUFFER_MAX`). Переполнение — потеря самых старых значений с ошибкой в логе; сервер продолжает работать.
- Срок хранения и сжатие задаются политиками TimescaleDB (`ARCHIVE_RETENTION_DAYS`).

## Резервирование
- Два узла с одинаковой конфигурацией. Роль (`primary` | `standby`) определяет `services/redundancy`. Оба узла опрашивают контроллеры и ведут `tagStore`.
- Пишет в контроллеры, архив и журнал только `primary`. На `standby` `commandGateway` отвечает `NOT_PRIMARY`.
- OPC UA — non-transparent redundancy: `ServerUriArray` и `ServiceLevel` (у `primary` выше).

## Надёжность
- Процесс не падает из-за ошибки драйвера, клиента или БД. `unhandledRejection` и `uncaughtException` пишутся в лог. После `uncaughtException` процесс завершается с ненулевым кодом, перезапуск выполняет systemd.
- Корректная остановка по `SIGTERM`/`SIGINT`: перестать принимать команды → остановить драйверы → дописать буфер архива → закрыть OPC UA и WebSocket → закрыть пул БД. Время остановки ограничено `SHUTDOWN_TIMEOUT_MS`.
- Обработчики не блокируют цикл событий: тяжёлая работа (импорт, отчёты, выборки архива) — асинхронно, с ограничением размера результата.
- Расчётная нагрузка: 80 установок, ≈ 2 000 тегов, опрос 1 с. Изменения, влияющие на производительность, проверяются нагрузочным тестом из `tools/`.

## Безопасность
- Все входящие данные (WebSocket, OPC UA, файлы конфигурации) проверяются схемами Joi до использования.
- Данные клиента не превращаются в пути файлов, SQL или имена объектов напрямую. SQL — только параметризованные запросы. Пути — только через проверку, что результат лежит внутри разрешённого каталога.
- Сеть BMS (контроллеры) и сеть клиентов — разные интерфейсы. Драйверы слушают и отправляют только в сети BMS (`BMS_INTERFACE`).

## Тесты
- Jest (`npm test`; запускать через `npm`, а не `npx jest`: скрипт добавляет флаг `--experimental-vm-modules` для node-opcua). На каждый новый или изменённый модуль создавать или обновлять тесты в `tests/`.
- Юнит-тесты не используют сеть, БД и реальные контроллеры: фейки и моки через параметры фабрик, временные каталоги (`os.tmpdir()`).
- На машине разработчика БД — эмулятор `tools/pgEmulator.js` (`npm run test:pg` — весь набор вместе с тестами БД). Общий PostgreSQL машины тесты и инструменты не трогают; рабочий PostgreSQL ставится на сервере объекта.
- Тесты с PostgreSQL работают каждый в своей временной схеме (`options=-c search_path=…` в адресе) и удаляют её, поэтому `TEST_PG_URL` может указывать на общую тестовую базу. Юнит-тесты шлюза, входа и OPC UA используют `tests/helpers/fakeUserStore.js`.
- Интеграционные тесты драйверов работают с эмуляторами из `tools/` на `127.0.0.1` и свободных портах. Тесты OPC UA поднимают сервер на свободном порту с временным каталогом PKI и подключаются настоящим клиентом node-opcua. Тесты `server.js`, которым OPC UA не нужен, задают `OPCUA_ENABLED=false`. Тесты с БД запускаются, только если задан `TEST_PG_URL`; иначе они пропускаются с сообщением.
- Тесты зависят только от `tests/setup.js` (`LOG_LEVEL=none`, тестовый `JWT_SECRET`, временный `DATA_DIR`). Глобальных моков нет. История вызовов моков очищается перед каждым тестом (`clearMocks`).
- Перед завершением работы прогонять весь набор.

## Версии
- Номер выпуска — поле `appVersion` в `package.json` сервера и клиента (одинаковый, формат `0.0.0.1`). Сервер пишет в лог при старте версию и короткий хеш коммита.
- Выпуск новой версии — по запросу пользователя: поднять `appVersion` в сервере и клиенте, добавить раздел в `README.md` («История» → `### version_X_X_X_X — ДД.ММ.ГГ`), поставить аннотированный тег `version_X_X_X_X`.
